## Why Descriptor Tests Exist

JUDO custom implementations wire their dependencies with OSGi DS `@Reference` annotations and register themselves with `@Component` annotations. Several invariants are expressed only in those annotations' attributes — service property filters (`target="(profile=stub)"`), cardinality (`ReferenceCardinality.OPTIONAL`), policy (`policy=DYNAMIC`), service properties (`property="profile=stub"`), service ranking, and so on.

**The Guice testkit cannot observe any of these attributes.** Two independent facts:

1. **`@Reference` has CLASS retention, not RUNTIME.** The testkit's own `ReferenceInjector` documents this in its Javadoc:

   > *OSGi's `@Reference` annotation has CLASS retention (not RUNTIME), so it's not available via reflection. Instead, this utility injects all non-static, non-final fields that have matching types in the Guice injector.*
   >
   > — `hu.blackbelt.judo.runtime.core.guice.testkit.util.ReferenceInjector`

   Reflection-based assertions like `field.getAnnotation(Reference.class).target()` therefore return `null` / do not compile against the annotation type at runtime. **You cannot write a "reflection contract test" for `@Reference` attributes.**

2. **`judo-runtime-core-guice-testkit` is not an OSGi DS container.** It wires Guice bindings by type, not by OSGi service-property filters. Whatever implementation is bound in the Guice module is what tests receive, regardless of any `target="…"` the production code declares.

So annotation-level DS invariants are a blind spot for DAO/service/custom-operation JudoTest tests. The authoritative surface that *is* observable in-process is the SCR component XML descriptor generated by `maven-bundle-plugin` from the annotations at `package` phase. That is exactly what Felix SCR evaluates at runtime in Karaf — asserting against it is the same contract, just read slightly earlier in the pipeline.

## When to Use

Use descriptor contract tests when you need to verify any DS-annotation attribute that the Guice testkit cannot see:

| Invariant | Annotation expression | Descriptor attribute |
|---|---|---|
| Service-property selector | `@Reference(target = "(profile=${app.profile})")` | `<reference … target="…"/>` |
| Reference cardinality | `@Reference(cardinality = ReferenceCardinality.OPTIONAL)` | `<reference … cardinality="0..1"/>` |
| Reference policy | `@Reference(policy = ReferencePolicy.STATIC)` | `<reference … policy="static"/>` |
| Service registration properties | `@Component(property = "profile=stub")` | `<property name="profile" …>stub</property>` |
| Service ranking | `@Component(property = "service.ranking:Integer=100")` | `<property name="service.ranking" type="Integer">100</property>` |
| Implementation class | `@Component class Foo` | `<implementation class="…Foo"/>` |
| Advertised service interfaces | `@Component(service = Foo.class)` | `<service><provide interface="…Foo"/></service>` |

Use JudoTest + `ReferenceInjector` (see [Getting Started](./getting-started.md)) for the **behavior** of the wired-up class — the Guice path exercises the method bodies. Use descriptor tests for the **wiring** of the class — the DS-XML path freezes the annotation-level contract.

## Where the Descriptors Live

During `mvn package` on the `…-application-app` module, `maven-bundle-plugin` (configured with `extensions=true` in the parent POM) runs bnd, scans every `@Component` class, and writes one XML file per component under `OSGI-INF/` in the produced jar:

```
application/app/target/northwind-app-<version>.jar
└── OSGI-INF/
    ├── com.<group>.<model>.custom.….MyCustomImplementation.xml
    ├── com.<group>.<model>.services.…OtherImplementation.xml
    └── …
```

The `application/integration-test` module already declares `…-application-app` as an upstream dependency (see `integration-test/pom.xml`). Because Maven builds `app` → `integration-test` in reactor order, the jar — and therefore every `OSGI-INF/*.xml` resource — is on the test classpath by the time `integration-test`'s `test` phase runs. A plain classpath lookup (`ClassLoader.getResourceAsStream("OSGI-INF/…xml")`) is all that is needed.

> **Orphaned-from-reactor build.** The `application/integration-test` module is intentionally not listed in `application/pom.xml`'s module tree; it is built standalone via `mvn -pl application/integration-test …` (or from the module directory). This is the established JUDO pattern (see rackinspect's `application/test/` for a richer example) and is what lets the tests consume the already-packaged upstream app jar without creating a reactor cycle with the `package`-phase bundle plugin.

## Complete Example

Below is a self-contained descriptor contract test that asserts four `@Reference` fields across four custom-operation classes all declare `target="(profile=${app.profile})"`. Adapt the resource paths, reference names, and expected filter to your project's invariants.

```java
package com.example.northwind.integration.dscomponent;

import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;
import org.w3c.dom.Document;
import org.w3c.dom.Element;
import org.w3c.dom.NodeList;

import javax.xml.parsers.DocumentBuilder;
import javax.xml.parsers.DocumentBuilderFactory;
import java.io.InputStream;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertNotNull;
import static org.junit.jupiter.api.Assertions.fail;

/**
 * Contract test for the profile-filter target attribute on selected {@code @Reference}
 * declarations. Operates on the SCR component XML descriptors emitted by
 * {@code maven-bundle-plugin} into {@code OSGI-INF/} of the packaged
 * {@code …-application-app} jar, because OSGi's {@code @Reference} has CLASS
 * retention and is therefore invisible to reflection-based assertions.
 */
class ProfileTargetFilterDescriptorTest {

    private static final String EXPECTED_FILTER = "(profile=${app.profile})";

    private static final String OP_A =
            "OSGI-INF/com.example.northwind.custom.….OperationACustomImplementation.xml";
    private static final String OP_B =
            "OSGI-INF/com.example.northwind.custom.….OperationBCustomImplementation.xml";

    @Test
    @DisplayName("OperationA#myService carries the profile filter")
    void operationA_myService_hasProfileFilter() throws Exception {
        assertReferenceTarget(OP_A, "myService", EXPECTED_FILTER);
    }

    @Test
    @DisplayName("OperationB#myService carries the profile filter")
    void operationB_myService_hasProfileFilter() throws Exception {
        assertReferenceTarget(OP_B, "myService", EXPECTED_FILTER);
    }

    /**
     * Loads an SCR component descriptor from the test classpath, finds the
     * {@code <reference>} element whose {@code name} matches, and asserts its
     * {@code target} attribute equals the expected LDAP filter.
     */
    private static void assertReferenceTarget(String resourcePath,
                                              String referenceName,
                                              String expectedTarget) throws Exception {
        ClassLoader cl = Thread.currentThread().getContextClassLoader();
        try (InputStream in = cl.getResourceAsStream(resourcePath)) {
            if (in == null) {
                fail("SCR component descriptor not on classpath: " + resourcePath
                        + " — this test must run after the '…-application-app' artifact has been"
                        + " packaged (mvn install).");
                return;
            }
            DocumentBuilderFactory dbf = DocumentBuilderFactory.newInstance();
            dbf.setNamespaceAware(true);
            DocumentBuilder db = dbf.newDocumentBuilder();
            Document doc = db.parse(in);

            NodeList refs = doc.getElementsByTagNameNS("*", "reference");
            Element match = null;
            for (int i = 0; i < refs.getLength(); i++) {
                Element ref = (Element) refs.item(i);
                if (referenceName.equals(ref.getAttribute("name"))) {
                    match = ref;
                    break;
                }
            }
            assertNotNull(match,
                () -> "No <reference name=\"" + referenceName + "\"> in " + resourcePath);
            String actual = match.getAttribute("target");
            assertEquals(expectedTarget, actual,
                () -> "Expected <reference name=\"" + referenceName + "\" target=\""
                        + expectedTarget + "\"> in " + resourcePath
                        + " but got target=\"" + actual + "\". Re-run the build to regenerate"
                        + " SCR descriptors after editing the @Reference annotation.");
        }
    }
}
```

### Asserting other descriptor attributes

The same XML-navigation pattern covers every attribute in the mapping table above. For component-level properties (service-property registrations, service ranking), target the root `<scr:component>` element and its `<property>` children:

```java
// Assert the implementation advertises profile=stub
NodeList props = doc.getElementsByTagNameNS("*", "property");
for (int i = 0; i < props.getLength(); i++) {
    Element p = (Element) props.item(i);
    if ("profile".equals(p.getAttribute("name"))) {
        assertEquals("stub", p.getTextContent().trim());
        return;
    }
}
fail("Component did not advertise property name=\"profile\"");
```

For cardinality / policy, read the attribute directly:

```java
assertEquals("0..1", match.getAttribute("cardinality"));
assertEquals("static", match.getAttribute("policy"));
```

## Running the Tests

The `application/integration-test` module is built standalone (not part of the default reactor). Two invocation styles, both valid:

```bash
# 1. From the module directory
cd application/integration-test
mvn -Dtest=ProfileTargetFilterDescriptorTest test

# 2. From the project root (must install the app first so its jar lands in ~/.m2/repository)
./judo.sh build
cd application/integration-test
mvn test
```

If you re-run `mvn test` without a fresh upstream `package`, the classpath will still carry the *previous* `…-application-app` jar — stale descriptors pass stale tests. Always pair descriptor contract tests with a fresh `./judo.sh build` (or at least `mvn -pl application/app install`) when verifying a change.

## Relationship to JudoTest / Guice Tests

These two test styles cover **different layers** and are complementary, not redundant:

| Dimension | JudoTest + Guice testkit | Descriptor contract test |
|---|---|---|
| Test annotation | `@JudoTest` (+ `@RegisterExtension JudoRuntimeExtension`) | Plain `@Test` |
| Dependency wiring | Guice injector binds by type | Asserted at XML surface only |
| What it proves | The class's methods produce correct behavior with the given dependencies | The class's wiring contract (what the OSGi container will read at runtime) is as intended |
| Sees `@Reference.target()` | No (CLASS retention, not Guice-modeled) | Yes (rendered to `<reference target="…"/>`) |
| Requires running app packaging | No — uses generated source on test classpath | Yes — consumes `OSGI-INF/*.xml` from the packaged app jar |
| Where tests live | `application/integration-test/src/test/java/…` | `application/integration-test/src/test/java/…` (same module) |

A healthy backend suite generally has both. Use JudoTest for "given these deps, does the operation do the right thing." Use descriptor contract tests for "is the OSGi wiring — target filters, cardinality, policy, service properties — frozen at the value we intend."
